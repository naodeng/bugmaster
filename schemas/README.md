# Contract Schemas

[中文版](README.zh-CN.md)

Schemas use JSON Schema Draft 2020-12. Contract tests check both the schema itself and representative documents.

## Implemented

- `oracle.schema.json`: validates a versioned expected-behavior record, target/feature applicability, and the SHA-256 digest and byte length of its source bytes. It does not authenticate the source or Oracle author.
- `evidence.schema.json` and `bugmaster_core.provenance.verify_provenance`: validate an evidence artifact fingerprint and exact references to an Oracle revision and local Action Journal outcome. The helper checks supplied source/artifact bytes, the canonical Oracle record digest, and the complete local Journal event chain. A match proves local integrity and reference binding only; its result keeps source authenticity `unverified` and the Confirmed Finding gate `blocked`. It is not persistent storage, a trusted adapter, a signer, or an authenticity verifier. `ActionJournal.recorded_outcome(action_id)` returns a validated local outcome binding but does not authenticate its origin or external result.

- `scope.schema.json`: validates the versioned Scope document, per-target authorization decision, known surfaces and risks, approval-reference presence for in-scope targets, and finite action budgets.
- `feature-inventory.schema.json`: validates the source-linked Feature Inventory emitted by the local OpenAPI CLI while keeping authorization and execution ledgers separate.
- `approval.schema.json`: validates scope or action approval records, exact scope revision and target binding, source/approver references, expiry fields, and the action intent fields required for R2.
- `action.schema.json`: validates the normalized action intent and lifecycle state, R0/R2 mutation constraints, R2 approval references, R1 mutation enforcement references, and non-executable mobile/unknown surfaces.
- `event.schema.json`: validates the Action Journal v1.1 envelope, including required `sessionId` and stable `journalId`, plus the four prepared/dispatched/outcome/reconciled payloads. The runtime additionally checks sequence, transition order, both identities, RFC3339 time, duplicate JSON keys, and the SHA-256 event chain. v1.0 records without `journalId` are rejected; there is no migration or in-place rewrite.
- `checkpoint.schema.json`: validates a checkpoint's immutable Session revision, Scope revision, and journal sequence/hash anchor, including the empty-journal edge case. It is structural validation; recovery must still verify the referenced revision and journal and recheck current authorization and budgets.
- `session.schema.json`: validates a versioned Session revision, canonical lifecycle status, scope revision history, approval references bound to scope revisions, budget ceilings and consumed counters, and Journal/Checkpoint references. The references do not establish authorization or recovery safety.
- `candidate-assessment.schema.json` and `bugmaster_core.candidate_assessment`: keep candidate screening decisions separate from Confirmed Findings, validate stable reason codes, append review feedback against a candidate revision and evidence, link deterministic cross-surface duplicates, and report precision/recall/review workload. `candidate` and `duplicate` are provisional local screening results; a host must verify provenance and canonical duplicate references before treating them as authoritative or suppressing/aggregating records. The schema reserves `rejected` for a future trusted-host flow; the current helper never emits it and rejects caller-supplied verifier callbacks. `candidate-assessment-rejected.json` is a schema-only fixture. This is a screening contract and in-memory helper, not a Finding store or evidence-authentication service.
- `candidate.schema.json`, `finding.schema.json`, and `bugmaster_core.metadata_store.CandidateStore` / `FindingStore`: validate and persist versioned Candidate/Finding metadata under a configured private root. Each record uses hashed ID directories, an owner-only POSIX lock, immutable revision files, a current head, canonical JSON digests, and optimistic revision checks. The store validates these schemas by default and can apply an additional caller validator. It rejects symlinks, hard links, unsafe owners, unsafe existing file permissions, extended ACLs detectable on macOS, history gaps, untracked entries, and digest mismatches. A missing configured root is created with owner-only access; an existing root must already be private and is never permission-repaired. Record directories may be repaired to owner-only access after ownership and ACL checks. Reads reject non-private directory modes, and unsafe existing files are always rejected without permission changes. Candidate `evidenceRefs` contain Evidence IDs; Finding `evidenceRefs` also contain SHA-256 digests and byte lengths. The store has no dedicated Evidence Blob field or byte-storage path; free-text fields can still carry raw or Base64-encoded evidence, which callers must keep out. Candidate assessment identity is bound to its Candidate revision and top-level Oracle reference; a Candidate cannot reference itself as a duplicate. Each review event must reference the same Candidate and an existing revision, and its evidence references must exist in that exact revision. Candidate `rejected` and Finding `confirmed`, `rejected`, `duplicate`, `resolved`, or `reopened` states remain blocked in storage. These local integrity checks do not authenticate evidence, source claims, or reviewer identity; they do not validate external references, suppress duplicates, connect the records to the Confirmed Gate, or create reports. Interrupted publication leaves an orphan or temporary entry and fails closed; this slice does not repair it automatically. Windows behavior is not verified.
- `bugmaster_core.session_store.SessionStore`: persists each validated Session revision as a separate immutable file under a private per-session directory. It serializes writers with a POSIX lock, writes through a synced temporary file, rejects replacement, sequence gaps, invalid permissions, and inconsistent revision transitions. `lock_revisions()` exposes the committed count and `lock_revision_snapshot()` exposes the count and latest revision while holding that same lock, so Journal initialization cannot race with first Session publication or bind a different Journal ID. Reads validate private directory ownership, mode, and ACL without mutation; writes validate ownership and ACL before repairing mode. Existing Session locks must have a private owner-only mode, no extended ACL, and no hard links. It does not authenticate Approval references, reconcile budgets against the Action Journal, or authorize resume. Windows behavior is not verified.
- `bugmaster_core.filesystem_security`: shared low-level ACL inspection for Session and Action Journal storage. On macOS it queries the descriptor ACL and fails closed when the ACL cannot be inspected; other platforms report no extended ACL through this macOS-specific check.
- `bugmaster_core.checkpoint_store.CheckpointStore`: persists each schema-validated Checkpoint under a hash of its ID in a private session directory. It shares the POSIX per-session lock, uses a synced temporary file and no-replace link, and rejects malformed records or Checkpoint directories with unsafe owners, mode, or ACLs. Reads do not repair existing paths. It does not verify that the referenced Session revision, Scope revision, or Journal head exists or is authentic, and it does not authorize resume. Windows behavior is not verified.
- `bugmaster_core.action_journal.ActionJournal.matches_prefix(sequence, head_hash)`: validates the complete local Journal before matching a Checkpoint prefix. It rejects duplicate JSON keys, symlinks, hard links, FIFOs, and non-regular files; pins each parent-directory component; and rechecks parent/file identities after lock acquisition and before success. Each instance syncs the directory chain before its first append and fails closed if an observed Journal disappears or is replaced. It parses JSONL by LF so Unicode line separators inside strings remain intact and accepts integral JSON number values as defined by the Checkpoint Schema. This is local integrity validation only; it does not establish provenance, source truth, authorization, or safe resumption.
- `bugmaster_core.action_journal_store.ActionJournalStore`: maps `sessionId` and `journalId` to `<root>/journals/<sha256(sessionId)>/<sha256(journalId)>.jsonl`. It walks the configured root and ancestors with no-follow directory-relative opens, checks trusted ownership and private mode bits (including the filesystem root), and rejects extended ACLs on macOS. It normalizes only root-owned `/tmp` and `/var` aliases with their expected targets; arbitrary ancestor symlinks fail closed. `initialize()` serializes Journal creation with Session publication using the per-Session lock. It creates and syncs a new private Journal only before a Session revision is persisted; afterward it only reopens the existing Journal and fails closed if the file or storage path is missing. Unsafe existing files are rejected without changing their permissions. `open()` also fails closed when a safe file is missing and never creates or repairs paths. Returned Journal instances retain the opened Session-directory descriptor and recheck its ACL before every read and append.
- `bugmaster_core.checkpoint_reference_validator.CheckpointReferenceValidator`: reads the stored Checkpoint and Session revisions under one shared lock and the same directory descriptors. It checks the Scope history anchor, latest `checkpointRefs` registration, and the Journal store's `journalId`, validates the storage root's trusted ancestors, and passes that same root descriptor through the Checkpoint/Session snapshot before opening the canonical Journal relative to it and verifying its prefix. Callers cannot select a different path for the declared IDs. This does not authenticate file content, event provenance, or external truth. It does not verify an authoritative Scope document, reconcile budgets, recheck authorization, or authorize resume.

`approvalRef` and `enforcementRef` are structural references only. Validation does not establish who approved a scope, whether the record is authentic, current, unexpired, or bound to this exact scope revision. The trusted authorization gateway must verify those properties before dispatch. R2 also needs action-level approval and enforceable controls; R3 remains subject to separate security policy.

The Session schema stores structural history and counters; `SessionStore` adds local immutable revision persistence and checks that stored references and counters evolve monotonically. A trusted recovery verifier must still authenticate approval references, reconcile budget counters with the immutable Scope revisions and Action Journal, verify the journal binding, and recheck current authorization before resume. JSON Schema does not compare consumed counters with their corresponding ceilings, and no trusted Session recovery verifier is implemented yet.

The local Action Journal uses restrictive file permissions, a single-operation POSIX file lock, append + `fsync`, and conservative recovery states. Its event hashes do not prove provenance or truth. A prepared/dispatched action without a result remains blocked after restart. Caller-supplied read-only observations are stored only as unverified reconciliation claims and never unlock dispatch or replay; R1/R2 failed outcomes also remain blocked. `scripts/validate_gates.py` denies all replay until a trusted read-only verifier and current-authorization gate are implemented.

## Candidate/Finding storage security limits

The digest chain detects partial or inconsistent edits, not a local actor with write access to the entire root who can recompute all digests or roll back the complete directory. Callers must keep raw or Base64-encoded Evidence content out of descriptive free-text fields. The store treats those fields as opaque text and does not inspect embedded content. Windows behavior is not verified, and direct extended-ACL inspection is macOS-specific.

Finding evidence references must use a unique Evidence ID within each revision, even when duplicate IDs carry different digests or byte lengths.

## Remaining contracts

Oracle/Evidence schemas and local binding checks are a first contract slice only: no durable Evidence Blob store, trusted adapter, source authentication, or Candidate/Confirmed Gate integration exists. Candidate/Finding metadata has local persistence and stores the linked Candidate Assessment, but the store is not integrated with the `assess_candidate()` helper, canonical duplicate lookup, trusted workflow, or reporting. The Candidate Assessment contract does not complete or replace those entity lifecycles. Its evidence references and verification flags remain structural inputs; the current helper cannot emit `rejected` until a trusted host verification path is integrated.

Oracle/Evidence schema structure tests are in `tests/contracts/test_provenance_schema.py`; they validate shape and field constraints, not source authenticity.

Skill Manifest, Pattern, Catalog, Capability Registry, Recovery Decision, durable Evidence Blob storage and authentication, trusted source adapters, authenticated Review records, report generation, Regression Recommendation, Eval Manifest, and Release Manifest remain unimplemented. Candidate/Finding metadata persistence does not complete those lifecycles or authorize decisions. The Candidate Assessment contract does not complete or replace those entities. Its evidence references and verification flags are structural inputs; the current helper cannot emit a `rejected` decision until a trusted host verification path is integrated. Trusted provenance still depends on real adapters. Existing status and identity guidance in `../docs/en/03-contracts.md` and `../docs/zh-CN/03-contracts.md` is the starting point. Do not treat this partial schema set as a passing complete contract suite.

Oracle, Evidence, Scope, Feature Inventory, Approval, Action, Event, Checkpoint, Session, Candidate Assessment, Candidate, and Finding schemas are exercised by contract tests in `tests/contracts/`. Candidate screening, review-event binding, rejection counter-evidence and benchmark mapping are covered by `tests/unit/test_candidate_assessment.py`, `tests/contracts/test_candidate_assessment_schema.py`, and `tests/contracts/test_contracts.py`; these tests do not establish evidence authenticity or run formal Eval cases. Candidate/Finding local persistence and filesystem checks are covered by `tests/unit/test_metadata_store.py`. Feature Inventory tests validate the actual CLI output generated from `examples/openapi/orders.json`; event tests validate actual journal output, including R2 approval binding. CheckpointStore persistence is exercised by unit tests in `tests/unit/test_checkpoint_store.py` and schema-backed contract integration tests. `CheckpointReferenceValidator` unit tests use real stores and test-only accept-all document validators; its schema contract test uses the real Checkpoint and Session Schema validators and verifies that integral JSON numbers in Checkpoint reference fields follow Schema integer semantics. These tests cover stored Session revision and Scope history references, latest Checkpoint registration, deterministic Journal ID-to-path resolution, and a local Journal prefix. They do not authenticate event content, verify an authoritative Scope document, establish trusted authorization, reconcile budgets, or authorize resume. SessionStore persistence is exercised by `tests/unit/test_session_store.py` and schema-backed Session contract integration tests; those tests do not exercise trusted authorization, budget reconciliation, or resume. CI installs the pinned `jsonschema[format-nongpl]==4.26.0` dependency; contract tests and default Candidate/Finding validators use it to execute RFC3339 timestamp checks. Python versions below 3.10 need to use the repository's Python 3.12 CI runtime or an equivalent compatible environment.
