# Contract Schemas

[中文版](README.zh-CN.md)

Schemas use JSON Schema Draft 2020-12. Contract tests check both the schema itself and representative documents.

## Implemented

- `scope.schema.json`: validates the versioned Scope document, per-target authorization decision, known surfaces and risks, approval-reference presence for in-scope targets, and finite action budgets.
- `feature-inventory.schema.json`: validates the source-linked Feature Inventory emitted by the local OpenAPI CLI while keeping authorization and execution ledgers separate.
- `approval.schema.json`: validates scope or action approval records, exact scope revision and target binding, source/approver references, expiry fields, and the action intent fields required for R2.
- `action.schema.json`: validates the normalized action intent and lifecycle state, R0/R2 mutation constraints, R2 approval references, R1 mutation enforcement references, and non-executable mobile/unknown surfaces.
- `event.schema.json` v1.1: validates the Action Journal event envelope, stable `journalId`, and four prepared/dispatched/outcome/reconciled payloads. The runtime checks sequence, transition order, Session and Journal IDs, RFC3339 time, and the SHA-256 event chain. v1.0 journal files are rejected without modification; no migration is provided.
- `bugmaster_core.action_journal.ActionJournal`: writes and reads v1.1 events for one immutable Session/Journal identity. If omitted, the Journal ID defaults to `journal-<sessionId>`; callers using a custom Session `journalId` must pass it to the constructor. `ActionJournalStore` resolves a canonical file from the storage root, Session ID, and Journal ID.
- `bugmaster_core.action_journal_store.ActionJournalStore`: maps a Session and Journal identity to `<root>/journals/<sha256(sessionId)>/<sha256(journalId)>.jsonl`. `initialize()` explicitly creates a new canonical empty Journal; `open()` reads an existing canonical Journal without creating or changing paths and fails closed when its storage or file is missing. No migration from earlier caller-selected paths is provided. The path and identity fields do not authenticate Journal contents.
- `checkpoint.schema.json`: validates a checkpoint's immutable Session revision, Scope revision, and journal sequence/hash anchor, including the empty-journal edge case. It is structural validation; recovery must still verify the referenced revision and journal and recheck current authorization and budgets.
- `session.schema.json`: validates a versioned Session revision, canonical lifecycle status, scope revision history, approval references bound to scope revisions, budget ceilings and consumed counters, and Journal/Checkpoint references. The references do not establish authorization or recovery safety.
- `bugmaster_core.session_store.SessionStore`: persists each validated Session revision as a separate immutable file under a private per-session directory. It serializes writers with a POSIX lock, writes through a synced temporary file, rejects replacement, sequence gaps, invalid permissions, and inconsistent revision transitions. It does not authenticate Approval references, reconcile budgets against the Action Journal, or authorize resume. Windows behavior is not verified.
- `bugmaster_core.checkpoint_store.CheckpointStore`: persists each schema-validated Checkpoint under a hash of its ID in a private session directory. It shares the POSIX per-session lock, uses a synced temporary file and no-replace link, and rejects malformed records. It does not verify that the referenced Session revision, Scope revision, or Journal head exists or is authentic, and it does not authorize resume. Windows behavior is not verified.
- `bugmaster_core.action_journal.ActionJournal.matches_prefix(sequence, head_hash)`: replays the current Journal through the existing event, transition, and hash-chain checks, then confirms whether the sequence/hash identifies a prefix. This is local integrity validation only; it does not establish event provenance, source truth, authorization, or safe resumption.
- `bugmaster_core.checkpoint_reference_validator.CheckpointReferenceValidator`: checks that a stored Checkpoint points to an existing immutable Session revision and Scope history entry, is listed by the latest Session revision, and matches a validated local Journal prefix. It requires an `ActionJournalStore`, checks its root and Session ID, compares its Journal ID with the latest Session revision, then opens only the deterministic path. It does not authenticate event provenance, recheck authorization or budgets, or authorize resume.

`approvalRef` and `enforcementRef` are structural references only. Validation does not establish who approved a scope, whether the record is authentic, current, unexpired, or bound to this exact scope revision. The trusted authorization gateway must verify those properties before dispatch. R2 also needs action-level approval and enforceable controls; R3 remains subject to separate security policy.

The Session schema stores structural history and counters; `SessionStore` adds local immutable revision persistence and checks that stored references and counters evolve monotonically. A trusted recovery verifier must still authenticate approval references, reconcile budget counters with the immutable Scope revisions and Action Journal, verify the journal binding, and recheck current authorization before resume. JSON Schema does not compare consumed counters with their corresponding ceilings, and no trusted Session recovery verifier is implemented yet.

The local Action Journal uses restrictive file permissions, a single-operation POSIX file lock, append + `fsync`, and conservative recovery states. Its event hashes do not prove provenance or truth. A prepared/dispatched action without a result remains blocked after restart. Caller-supplied read-only observations are stored only as unverified reconciliation claims and never unlock dispatch or replay; R1/R2 failed outcomes also remain blocked. `scripts/validate_gates.py` denies all replay until a trusted read-only verifier and current-authorization gate are implemented.

## Remaining contracts

Skill Manifest, Pattern, Catalog, Capability Registry, Recovery Decision, Oracle, Evidence, Finding, Review, Report, Regression Recommendation, Eval Manifest, and Release Manifest remain unimplemented. Existing status and identity guidance in `../docs/en/03-contracts.md` and `../docs/zh-CN/03-contracts.md` is the starting point. Do not treat this partial schema set as a passing complete contract suite.

Scope, Feature Inventory, Approval, Action, Event, Checkpoint, and Session schemas are exercised by the corresponding tests in `tests/contracts/`. Feature Inventory tests validate the actual CLI output generated from `examples/openapi/orders.json`; event tests validate actual journal output, including R2 approval binding. CheckpointStore persistence is exercised by unit tests in `tests/unit/test_checkpoint_store.py` and schema-backed contract integration tests. `CheckpointReferenceValidator` tests use the real local stores to check Session revision, Scope history, latest Session registration, deterministic Journal path resolution, and Journal-prefix consistency. This remains local structural validation: it does not authenticate Journal contents, establish event provenance, verify trusted authorization or budget reconciliation, or authorize resume. SessionStore persistence is exercised by `tests/unit/test_session_store.py` and schema-backed Session contract integration tests; those tests do not exercise trusted authorization, budget reconciliation, or resume. CI installs the pinned test validator and runs the contract suite. To run it locally, use Python 3.12 and install `jsonschema[format-nongpl]==4.26.0`; the optional format validators make RFC3339 timestamp checks executable. This is a test-only dependency and is not a BugMaster runtime dependency. Python versions below 3.10 need to use the repository's Python 3.12 CI runtime or an equivalent compatible environment.
